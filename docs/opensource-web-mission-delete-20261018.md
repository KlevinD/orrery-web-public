# WEB/API 删除回写回归与开源准备（2026-10-18）

本阶段修复 Mission 删除后被迟到的 projection 写入重新创建的缺口。修改前基点为 `86389cdf5b27bff0b423a94c9154fcf15a120052`。本阶段仅处理私有 WEB/API 候选；没有运行 CI、合并、部署、公开发布或查询线上。

## 问题与修复

后台运行事件投影会先读取 Mission，再计算和保存新版本。旧的 `SaveForTenant` 在记录不存在时直接执行 upsert；删除只移除记录，因此“读取、删除、迟到保存”能够重新插入 Mission。新增确定性回归在旧实现上验证了这一点，包括关闭并重新打开文件数据库后的写入。

现在删除与保存使用同一个规范键事务锁。删除在同一 core 数据库事务中写入租户隔离的删除标记，并移除 projection；保存发现标记后返回 `ErrProjectionNotFound`。全局历史裸键与规范键同时存在时一并删除。标记不进入 Mission 列表表；删除未知 ID 不会预占 ID，其他租户仍可创建同名 Mission。

该修复保护经当前 repository 执行的删除，不回补历史已删除 ID。删除标记随数据库持久保存，同一租户已删除的 Mission ID 不再复用；部署时需让所有写入实例使用识别标记的版本。权限、用户委托、Agent 身份、任务终止、QA 与发布门禁继续经过既有业务链。

## 验证边界

新增回归覆盖迟到保存、数据库重开、列表隐藏、租户隔离、未知 ID 的后续创建，以及全局历史记录格式。旧实现确定性失败，修复后 Windows 相关包检查为 864 通过、3 跳过；Linux 完整 server、runtime、Mission 与 Discussion 检查为 3393 通过、19 跳过、0 失败，退出码 0。原端到端故障测试单独重复 30 次全部通过。计数包含子测试；使用 Go 1.25.0、CGO_ENABLED=0，Linux 容器禁用网络，未调用外部商业模型。

上阶段的端到端偶发失败发生在删除讨论后 Mission 仍被列出的断言。临时诊断版本重复 30 次均通过，没有捕获当次失败的实际时序，因此不能断言每次历史失败均来自同一原因。临时日志已撤下，原测试断言、超时和后台工作器保持原样。没有运行 race、真实 PostgreSQL 并发集成或全库 `./...`；SQLite 回归与事务代码审阅不能替代这些验证。
