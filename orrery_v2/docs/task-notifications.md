# 任务成果订阅与通知

前端入口为侧栏「通知」(`/notifications`)。自动化任务行的铃铛进入该任务的订阅页；个人设置也可进入接收偏好。

- **任务成果**：个人站内收件箱、未读数量、成果摘要、已验证报告下载。
- **我的订阅**：订阅后续执行结果，独立选择个人微信或飞书，也可额外接收无报告的失败结果。
- **接收偏好**：组织通知的外部推送渠道，默认只接收站内通知。绑定状态来自当前账号真实的渠道绑定。
- **任务通知设置**：具有 `scheduler.write` 或 `operations.manage` 的组织负责人可配置仅订阅者、指定人员、组织全员，查看接收人数及最近 25 次通知的逐人投递记录。

组织全员仅包含当前组织启用的真人档案，排除 AI 和保留的系统账号。通知只分享业务摘要和已归档报告；内部日志不在授权范围内。每条通知的读取、已读状态、报告下载均按当前身份及租户校验。指定名单移除人员后，已有结果的分享权限也会撤回。

只有受信任的内部系统身份能够新增跨租户成果发布关系，例如将 `system` 中的铁蛋日报发布给 `minvia`。组织负责人可管理已经授权发布到本组织的接收范围，不能自行引入其他租户的任务。

## 投递语义

后台从调度器已提交的终态结果生成通知，不触发 Agent 执行。任务须在规则启用后启动；个人订阅须在该次任务启动前开启，因此保存配置不会补发历史结果。普通失败默认不广播，任务受阻但具备本次执行验证并归档的报告则显示「报告已生成 · 部分步骤未完成」。任务的失败状态继续保留。

发布事件、个人收件箱和待推送记录在一个短数据库事务中提交。事件按发布关系和运行 ID 去重；收件箱按事件、租户、真人去重；外部推送按收件箱和渠道去重。组织通知和订阅重叠时只产生一条收件箱记录。个人订阅启用时，它的渠道选择优先于组织通知接收偏好。

发送使用现有 Gateway 持久化队列和幂等键，不调用模型。微信和飞书独立入队，未绑定的渠道等待绑定后恢复。发送前再次检查成员状态、通知规则和偏好。队列处理失败显示投递状态；站内成果仍可阅读。「站内已读」和「渠道已送达」分别记录，不等同于外部消息被阅读。

现有调度任务的 `delivery` 设置保持兼容。为同一任务接入统一通知时，应明确保留还是停用旧渠道规则，避免另一路群通知与个人推送同时发送。首批仅配置所需任务，不自动开放全部任务，不自动订阅全部人的外部渠道。

## 运维与验证

新增 `notification_*` 表为独立的增量表，位于 core 数据库。回滚旧服务不会删除这些记录。扫尾器 `task.notifications` 在下一次周期恢复未发布结果和未完成投递；使用调度器缓存的运行快照，无需读运行轨迹。配置更新使用 revision 防止覆盖他人修改。

接口契约在 `docs/api/mission-control.openapi.yaml`，前端类型由其生成。重点测试覆盖组织边界、真人筛选、订阅与组织去重、历史抑制、部分成果、逐人已读、报告授权、渠道独立恢复、发送前撤权和管理者投递历史。浏览器验证使用独立本地夹具，不向生产接收人发送测试消息。

当前版本覆盖调度器的 Agent 任务成果。按部门批量选人、定时摘要、职责规划产物的独立发布和人工补发属于后续扩展。
