# RSI：生产终态反馈恢复

生产任务的真实请求已经按 attempt 捕获。本阶段补充终态到 RSI 账本之间的故障恢复，保证已经写入宿主日志的终态可以在数据库恢复或服务重启后继续提交。

## 运行流程

1. 生产讨论、mention 和任务队列共享一个 `RuntimeFeedbackJournal`。已有 trace 收尾后，将最小终态写入 `BaseDir/data/rsi-runtime-feedback`。文件名由租户与 attempt 的 SHA256 生成，每个文件最多 128 KiB；只包含租户、尝试、原请求引用、状态、时间、耗时、token 用量和 trace 收尾状态，不包含 prompt、输出、错误正文或密钥。
2. 在 Linux 宿主上，先以独占临时文件写入并 fsync，再通过硬链接原子发布最终文件并 fsync 目录。同一 attempt 的不同内容不能覆盖最先持久化的终态。哈希用于检测内容错误，宿主及其私有目录仍是信任边界。
3. 沿用原有数据库事务，一起提交终态、Observed Case、不可变修订和 Ontology 投影 outbox。成功后删除并确认对应日志。删除失败会保留供恢复器重试；它不会将已提交业务结果改为运行器失败。
4. 平台底层 sweeper `ontology.runtime_feedback_recovery` 分批扫描日志，重新读取原始请求，核对租户、attempt、RequestID、终态内容、时间及用量，再使用相同数据库事务补齐反馈。默认每次最多处理 100 个目录条目，沿用平台 batch size，最高 1,000 个；一次 sweep 的上下文上限为 5 秒。
5. 重复记录、数据库提交成功后进程退出、多恢复器同时看到同一记录，都由现有不可变终态与案例幂等规则处理。确认后移除日志，不重复新增 Case、修订或 outbox。

恢复器只操作反馈证据和账本。它不调用模型、运行器、交付接口或业务任务执行入口。底层投影 sweeper 会继续将恢复的 outbox 送入正常 Ontology 流程。

## 故障处理

- 数据库不可用而日志写入成功：保留日志，原错误沿用 BaseAgent 的 post-commit 分类；数据库恢复后补写反馈。
- 日志磁盘不可写而数据库可用：仍尝试原有数据库事务，提交成功则保留正常任务结果。
- 日志与数据库都失败：错误保持可见，本阶段无法保证该终态被保存。
- 日志冲突、损坏、错误租户、找不到原请求、无效状态或用量：保留并报告错误，不覆盖先前证据。扫描游标会继续前进，避免坏记录永久挡住后续正常记录。
- 没有终态日志的 prepared 请求：继续保持 `terminal: null`，不依据时间、另一次重试或最新注册表推断结果。
- 服务在日志最终文件发布前崩溃：仍可能只有 prepared 证据。临时 `.tmp` 文件不作为终态证据，也不会被自动采用；它们需要运维清理。
- 宿主永久丢失或本地持久盘损坏：本地日志也可能丢失；本阶段未实现跨主机日志复制。

确认完成的日志会删除。未确认记录保留以便恢复，不设自动丢弃期限；仍需后续容量监控与保留治理。日志不会自动进入模型上下文，也不会触发历史记忆注入。

`DisableBackgroundWorkers` 模式不创建日志目录或注册恢复器。生产目录随 shared 数据存储，跨二进制版本切换和普通服务重启保留；回退到不支持此日志的旧版本时，日志保留，须恢复支持的版本后继续处理。

## 验收范围

测试覆盖断库后重新打开、重新建立文件扫描器、提交后未清理的日志、重复恢复、并发文件写入、并发 PostgreSQL 恢复、事务回滚、冲突终态、租户隔离、损坏记录、按批次继续扫描和 Linux 符号链接拒绝。生产工厂测试用替代 provider 触发 post-commit 故障，再通过生产 sweeper 补齐反馈，并确认 provider 与业务交付均只执行一次。

这完善真实任务反馈到 Ontology 改进账本的可靠性。业务归因、冻结完整基线、生产准入队列、各领域原生改进执行器、独立业务评价和全域自动发布仍需继续接入。
