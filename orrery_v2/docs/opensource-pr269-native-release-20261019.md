Activation uses the already deployed production release guard, all five existing deployment locks, and a fresh expected production commit. It pauses only new repair claims while existing execution drains. Builds and file preparation happen before taking the activation lease. The API binary, source snapshot, static Web archive and validation record are retained together with their hashes and the previous release reference.

The existing public Web file routing was pinned to an older release directory even though `/current/web` referred to a newer build. Activation atomically exchanges that directory with a link following `/current/web`; the original directory is retained for exact rollback. An append-only immutable asset archive preserves files needed by already open browser pages. Verification compares the public index and each referenced entry resource with the new files, checks API readiness and unauthenticated rejection, and verifies unchanged service configuration, scheduled task configuration and deployed repair worker hashes. A failed activation restores the original Web directory and API release.

The final deployed commit, running binary hash, public Web hashes, health counts and configuration preservation receipts are recorded in `DEPLOYMENT_RESULT.json` and `BUILD_MANIFEST.json` beside the production release and in the local deployment artifacts. Real external model calls, external MCP acceptance, desktop signing and actual channel delivery are separate acceptance layers. This release does not replay excluded historical tasks or infer business completion or channel delivery from technical readiness.
