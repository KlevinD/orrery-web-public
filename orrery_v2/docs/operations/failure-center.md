# 故障采集与明细

入口：`/resources/ontology/reliability`。选择故障后，“最近错误明细”显示最近 20 条已脱敏的原因、堆栈、请求编号和运行编号。摘要沿用现有读取权限，明细要求当前范围的管理权限。故障仍通过现有可靠性服务进入问题中心和本体投影。

- 登录后的网页捕获 JavaScript 错误、未处理的 Promise 拒绝以及 API 网络失败。每个账号最多保留 20 条待上报记录，恢复联网或每 60 秒重试。请求中不携带业务请求体、Cookie、授权头；服务端从当前登录会话确定账号和范围。
- 接口保留 MapError 前的原始原因，返回唯一请求编号。panic 写入脱敏堆栈；已开始发送的响应会中止，避免返回一个看似完整的成功结果。
- 运行日志的 ERROR，以及带错误原因的 WARN，写入磁盘收件箱。常规慢请求告警不进入故障队列。同一日志的控制台和文件输出只采集一次；相同故障沿用现有指纹合并发生次数。
- Agent 失败后的状态保存和故障发布使用独立于执行取消信号的上下文；任一步失败都会返回调用方。失效的执行租约不再直接取消故障记录。
- systemd 日志输出带正确的 ERROR/WARN 优先级，JSON 文件日志格式保持可读。

磁盘目录位于 `filestore.root/diagnostics/failure-inbox`，权限为目录 0700、文件 0600。`pending` 最多 10,000 条；`history` 保留最近 2,048 条已投递记录；损坏的记录移入 `quarantine` 并报告错误，不阻塞其他有效记录。投递使用现有基础维护循环中的后台工作器，不调用 LLM。数据库不可用时保留待投递记录；提交后应答丢失、重启和浏览器重试均复用观察编号，避免重复计数。

这不是全量日志备份：登录前的浏览器错误、进程启动前的错误、绕开统一日志器的输出、系统 OOM/SIGKILL 需要结合浏览器控制台、journald 和进程监控排查。磁盘满或不可写时会保留原始日志并输出收件箱写入失败；浏览器禁用存储时仅提供内存重试。历史明细按容量保留，不补录发布前的旧日志。
