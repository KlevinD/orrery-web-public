Orrery 商业企划书 v0

生成日期：2026-05-31

1. 核心理念

未来的组织不再只是“人使用工具”，而是“人、AI Agent、外部工具、组织规则共同组成一个可运转的工作系统”。

过去的软件主要帮助人提高效率。下一阶段，AI Agent 会逐渐承担一部分真实工作：理解任务、调用工具、推进流程、生成成果、请求审批、接受验收。企业面临的新问题不再只是“有没有更聪明的 Agent”，而是：

如何把 Agent 变成可管理、可授权、可评价、可追责的组织成员？

Orrery 的出发点是：Agent 不是普通工具，而是新的工作主体。工具只执行动作，Agent 承担任务、沟通、总结、交付和被评价。企业真正需要的不是更多孤立 Agent，而是一套能管理“人 + Agent + 工具 + 组织规则”的控制平台。

2. 反共识观点

我们相信：

Agent 的瓶颈不是智能，而是组织化。

模型会越来越强，单点 Agent 会越来越多，工具调用会越来越方便。但企业真正采用 Agent 时，最大的阻力会变成：

  • 谁能调度 Agent？
  • Agent 能代表谁行动？
  • Agent 能调用哪些工具？
  • 哪些动作必须经过人审批？
  • 结果出了问题谁负责？
  • 管理者如何验收和审计？
  • Agent 的表现如何被持续评价？

因此，未来企业不会缺 Agent，企业会缺少管理 Agent 的组织系统。

3. 一句话定位

Orrery 是人机共生组织控制平台，
帮助企业建立、调度和治理由真人与 AI Agent 混编的数字劳动力。

面向客户，它是一个可审计任务交付工作台。

面向企业，它是一个人机组织控制面。

面向 Agent 和工具生态，它是一个权限、审批、审计和证据网关。MCP Gateway 是后续企业版与收费方向，不作为第一阶段主卖点。

4. 为什么现在是机会

AI Agent 正在从“回答问题”走向“执行工作”。这个变化带来三个确定趋势。

第一，单点 Agent 正在快速成熟。软件开发、销售、客服、财务、法务、运营等场景里，都已经开始出现可执行任务的 Agent。

第二，工具调用正在成为基础能力。MCP、API、RPA、浏览器自动化、企业 SaaS 连接器，让 Agent 不再停留在聊天框里，而是能接触真实业务系统。

第三，企业开始面对治理问题。只要 Agent 能调用真实工具，就必然出现权限、审批、数据泄露、误操作、审计、责任归属和人工介入问题。

这意味着，市场竞争正在从“谁有更强 Agent”扩展到“谁能安全、可控、可审计地使用 Agent”。Orrery 的机会就在这个上层控制面。

5. 客户痛点

当前企业和团队使用 AI Agent 时，痛点不是缺少工具，而是工具过多、责任分散、结果不可控。

典型问题包括：

  • Agent、自动化脚本、外包人员、内部员工各自工作，过程分散。
  • 管理者不知道哪个 Agent 正在做什么、做到哪里、缺什么信息。
  • Agent 输出只有结论，没有证据，客户无法判断是否可信。
  • 任务失败后无法定位责任，是需求问题、工具问题、Agent 理解问题，还是 QA 标准问题。
  • 工具调用缺少统一权限判断，Agent 可能越权、误调或泄露数据。
  • 人类介入只是临时弹窗，不是可追踪、可恢复、可评价的业务流程。
  • 真人和 Agent 的交付格式不同，协作成本高。
  • 多 Agent 任务上下文无限膨胀，客户看不到干净成果。

客户需要的不是“更多 Agent”，而是一个能让 Agent 真正进入组织工作的控制系统。

6. 产品方案

Orrery 的产品由九个核心模块组成。

模块作用
People Directory管理真实人员、身份、岗位、组织归属
Organization Graph管理部门、角色、汇报关系、项目组织
Agent Directory管理 Agent 档案、能力、工具、owner、状态
Mixed Squad让真人和 Agent 组成可调度团队
Mission Control把客户目标转成任务、责任、进度、交付和证据
Permission Center判断某个主体在某个上下文里能不能做某个动作
HIL / Approval Center把人类介入、审批、补充信息和流程恢复产品化
Tool / MCP Gateway统一管理 Agent 对外部工具的调用、凭证、审计和风险；MCP 是后续增强方向
Evaluation Center评价人、Agent、Squad 的任务表现和协作质量

这九个模块组成一个闭环：

需求进入
  -> 组建人机团队
  -> 分配责任
  -> Agent / 真人执行
  -> 工具调用进入权限与 HIL
  -> 提交成果、摘要和证据
  -> QA 验收与客户确认
  -> 沉淀评价和组织能力

7. 产品形态

早期客户看到的不是复杂平台，而是一个 Mission 工作台。

客户提交一个目标，例如：

  • 做一份竞品监控周报。
  • 筛选销售线索并更新 CRM。
  • 处理一批复杂客服工单。
  • 初审合同并标出风险。
  • 完成一个自动化任务并交付验证结果。

Orrery 负责组建一个人机混编团队，拆分任务，分配责任，执行工作，触发审批，收集证据，组织验收，最终交付一个可读的结果包。

最终交付包包括：

  • 最终成果。
  • 执行摘要。
  • 责任清单。
  • 关键证据。
  • 工具调用与审批记录。
  • QA 验收结果。
  • 风险、阻塞和后续建议。

客户不需要阅读完整 Agent 日志，也不需要理解底层工具编排。客户购买的是可信交付，而不是自动化过程本身。

8. 核心竞争力

8.1 把 Agent 当组织成员，而不是工具节点

大多数 workflow 产品把工具调用当成节点。Orrery 的核心不同：工具不是成员，Agent 才是成员。

每个 Agent 都必须能够：

  • 接收任务。
  • 理解上下文。
  • 沟通与回复。
  • 调用工具。
  • 提交 summary。
  • 提交 deliverable。
  • 提交 evidence。
  • 接受 QA。
  • 形成历史表现。

这使得系统管理的是“责任主体”，而不是工具流程图。

8.2 人和 Agent 使用同一套交付协议

真人不是旁路审批按钮，Agent 也不是假装成人。二者都以同一套协作协议进入任务：

summary
deliverable
evidence
blocking
approval
review

这会抹平人和 Agent 在项目管理里的协作差异，让客户只关心谁负责、交付了什么、证据是什么、是否通过验收。

8.3 组织规则进入 Agent 执行过程

Agent 不能只靠 prompt 约束。Orrery 把组织规则放进执行链路：

  • 谁能创建任务。
  • 谁能调度某个 Agent。
  • Agent 能代表谁行动。
  • Agent 可以调用哪些 MCP 工具。
  • 哪些动作必须 HIL。
  • 哪些审批节点必须由真人处理。
  • 哪些结果必须 QA。

这让企业可以放心把 Agent 放进真实业务流程。

8.4 证据链，而不是幻觉总结

Orrery 的原则是：

summary 不是信任源，evidence 才是信任源。

每个任务交付都必须绑定证据。证据可以是文件、截图、链接、工具调用记录、审批动作、测试结果、客户确认、QA 结论。

这让 Agent 输出从“看起来合理”变成“可以被验收”。

8.5 Tool Gateway、HIL 与后续 MCP 控制面

随着 tool calling、自动化脚本、内部系统 API 和 MCP 普及，Agent 调用外部工具会成为企业 AI 的关键风险点。

第一阶段不把 MCP Gateway 当成主卖点，而是先做“工具调用可控、关键动作可审批、执行结果可留痕”。当企业开始接入更多内部工具和 MCP Server 后，Orrery 可以自然升级为统一控制面：

Agent Runtime
  -> Orrery MCP Gateway
  -> Permission Decision
  -> HIL / Approval if needed
  -> Downstream Tool / MCP Server
  -> Audit / Evidence

下游工具不需要各自重复实现企业权限、审批、凭证托管和审计。Orrery 承担这一层，但这个能力应作为中后期收费和企业版壁垒，而不是当前宣传入口。

9. 商业壁垒

Orrery 的长期壁垒不来自某个模型，也不来自某个单点 Agent，而来自组织控制数据和执行闭环。

9.1 组织事实源壁垒

当 People、Agent、Squad、Department、Role、Mission、Permission 之间形成稳定关系后，Orrery 会成为企业人机组织的事实源。

这类数据迁移成本高，且会持续影响权限、审批、评价和任务分派。

9.2 任务交付数据壁垒

每次 Mission 都会沉淀：

  • 哪类任务需要哪些角色。
  • 哪些 Agent 适合哪些任务。
  • 哪些交付物最容易通过验收。
  • 哪些证据最能支撑结果。
  • 哪些流程容易返工。
  • 哪些人类介入最关键。

这些数据会不断提高后续任务交付质量。

9.3 权限与 HIL 策略壁垒

企业一旦把 Agent 权限、审批、HIL 和工具调用策略配置进 Orrery，系统就会成为 AI 执行的安全中枢。

这不是简单 UI，背后是组织规则、业务风险和审计要求的沉淀。

9.4 工具与 MCP 生态入口壁垒

如果 Orrery 能成为企业接入内部工具、自动化脚本和 MCP 工具的统一网关，它就能沉淀：

  • MCP Server 注册信息。
  • Tool 风险画像。
  • Tool call 审计。
  • 凭证托管关系。
  • 授权策略。
  • 调用成本、延迟、失败率。

这会让 Orrery 从任务系统扩展为 Agent 工具生态控制层。

9.5 评价数据壁垒

人、Agent、Squad 的表现评价会形成长期数据资产：

  • 任务成功率。
  • QA 分数。
  • 返工次数。
  • 人工接管率。
  • HIL 触发率。
  • 工具调用成功率。
  • 客户满意度。
  • 协作可靠性。

这让系统越来越知道“什么任务该派给谁”。

10. 数据飞轮

Orrery 的飞轮是：

更多 Mission
  -> 更多人机协作数据
  -> 更准的任务拆分和 staffing
  -> 更可靠的权限/HIL 策略
  -> 更高的交付验收率
  -> 更强的客户信任
  -> 更多 Mission

这个飞轮的关键不是收集更多聊天记录，而是沉淀结构化的任务、角色、工具、证据、审批和评价数据。

11. 为什么我们能赢

Orrery 的竞争优势不在于做一个更强模型，也不在于比现有 Agent 更会写代码、聊天或调用工具，而在于对“Agent 如何进入真实组织工作”的理解更完整。

11.1 选对战场：不卷单点 Agent

单点 Agent 会持续被大模型厂商、SaaS 巨头和垂直工具厂商压缩。Orrery 不和 Codex、Claude Code、Cursor、Copilot Studio、Agentforce 正面竞争执行能力，而是把它们当作可接入的劳动力。

这让 Orrery 避开最拥挤的模型和 Agent 能力竞争，转向更上层的组织、责任、权限、证据和评价。

11.2 选对切口：从人事和运维的项目化交付进入

直接切企业 AI CoE 或 MCP Gateway 治理，容易陷入漫长的安全评审、系统适配和平台化需求。Orrery 先从人事和运维场景进入，因为这里同时具备：

  • 高频重复任务。
  • 明确责任边界。
  • 明确审批和留痕要求。
  • 跨系统、跨人员协作。
  • 客户能理解的项目化交付价值。

这使得早期可以用具体任务证明价值，而不是先卖抽象平台。

11.3 选对抽象：Agent 是组织成员，不是工具节点

许多自动化产品从流程图和工具调用出发，容易变成复杂 workflow builder。Orrery 从组织主体出发，先定义谁负责、谁协作、谁审批、谁验收，再让工具服务于这些主体。

这个抽象更贴近企业真实管理方式，也更容易扩展到真人、Agent、外包专家和自动化工具混合协作。

11.4 选对信任机制：证据链优先

客户真正不信任的不是 AI，而是“无法验证的 AI 结果”。Orrery 把 summary、deliverable、evidence、QA、approval 作为统一交付协议，让每次任务都能被追踪、验收和复盘。

这会把产品从“AI 生成答案”变成“AI 交付可验收工作”。

11.5 选对扩展路径：先交付，再治理

Orrery 的路线不是一上来做重型平台，而是：

人事/运维项目化交付
  -> 可审计 Mission 工作台
  -> 人机团队与 Agent Directory
  -> 权限、HIL 与工具网关
  -> MCP Gateway 与企业治理
  -> 评价和组织运营系统

这条路径既能早期卖项目，又能保留长期平台想象力。

12. 目标客户

12.1 早期客户

最适合早期切入的是企业内部已经存在大量重复、跨系统、跨人员协作任务的人事和运维场景。

客户购买理由
人事 / HR 运营团队入转调离、招聘协同、员工信息收集、审批和通知经常跨系统、跨人员
IT / 运维团队账号开通、权限变更、工单处理、资产巡检、故障协同需要留痕和审批
行政 / 综合运营团队供应商、资产、办公流程和内部服务事项需要多人协同和结果归档
中小企业管理团队没有成熟流程平台，但有大量“需要有人跟进到底”的内部事务

12.2 中后期客户

中后期可以进入更高客单价场景。

客户购买理由
企业 AI CoE需要治理企业内部越来越多的 Agent；但不作为第一切入口
自动化中心需要统一任务、权限、审批和工具调用审计
IT / 安全团队需要控制 Agent 对内部系统和 MCP 工具的访问
MCP 工具服务商需要复用 Orrery 的权限、HIL、审计和凭证托管能力

13. 第一切入口

建议第一阶段不要直接销售“大型人机组织平台”，也不要直接切企业 AI CoE / MCP Gateway 治理。后者容易陷入无尽适配、集成和安全评审，销售周期长，早期反馈慢。

第一阶段应销售更容易理解、可项目化交付的结果：

人事与运维场景的可审计任务交付工作台

原因：

  • 人事和运维天然需要跨人、跨系统、跨审批协作。
  • 这些场景有明确任务入口、责任人、审批节点、交付物和留痕需求。
  • 客户能理解“有人帮我把这件事推进到底”的价值。
  • 可以项目化交付，不必一开始做标准 SaaS 定价和复杂销售。
  • 不需要一开始打穿全部 MCP/AI CoE 治理体系，避免陷入底层适配泥潭。
  • 成功后可以自然扩展到权限、HIL、工具网关和企业治理。

第一阶段要证明：

客户愿意为“人事/运维任务的可追踪、可验收、可审计交付”按项目付费。

14. 明确场景与案例

第一阶段不要抽象销售“人机共生组织控制平台”，而是包装成客户能直接购买的任务包。每个任务包都要有明确输入、执行过程、交付物和验收标准。

14.1 人事场景一：新员工入职交付包

适用客户：中小企业 HR、快速扩张团队、连锁门店总部、外包/实习生较多的公司。

客户输入：

  • 新员工名单。
  • 入职日期。
  • 岗位、部门、直属上级。
  • 需要开通的系统账号。
  • 办公设备和权限需求。
  • 入职材料模板。

Orrery 执行：

  • HR Agent 检查入职信息是否完整。
  • IT / 运维 Agent 生成账号、权限、设备准备任务。
  • 行政 Agent 生成工位、门禁、物资准备任务。
  • 通知 Agent 给新人、直属上级、行政和 IT 发送待办。
  • QA Agent 检查所有入职事项是否有结果和证据。

交付物：

  • 每位新员工的入职准备清单。
  • 缺失信息列表。
  • 账号开通和设备准备记录。
  • 入职通知发送记录。
  • 未完成事项和责任人。
  • 最终入职交付报告。

客户购买理由：

HR 不再靠微信群、Excel 和反复催办推进入职。每个新人是否准备好、卡在哪里、谁负责，一眼可查。

14.2 人事场景二：员工离职与权限回收包

适用客户：重视权限安全、人员流动频繁、外包人员较多的团队。

客户输入：

  • 离职人员名单。
  • 离职日期。
  • 所属部门和直属上级。
  • 已知系统账号。
  • 资产领取记录。
  • 交接要求。

Orrery 执行：

  • HR Agent 建立离职 Mission。
  • IT Agent 识别需要关闭或转移的账号权限。
  • 行政 Agent 追踪设备、门禁卡、工牌等资产回收。
  • 直属上级或业务负责人确认工作交接。
  • HIL / 审批节点处理高风险权限、重要资料和延期回收。
  • QA Agent 检查权限、资产、交接、证明材料是否完整。

交付物：

  • 离职流程完成报告。
  • 权限关闭/转移记录。
  • 资产回收记录。
  • 工作交接确认。
  • 异常项和未关闭风险。
  • 可审计证据包。

客户购买理由：

离职最怕“人走了，账号还在，资产没回，交接没人认”。Orrery 把离职流程变成可追责交付，而不是口头确认。

14.3 人事场景三：招聘协同与候选人推进包

适用客户：招聘量不大但流程混乱的中小企业、业务负责人直接参与招聘的团队。

客户输入：

  • 岗位 JD。
  • 候选人简历。
  • 面试官名单。
  • 面试时间偏好。
  • 评价模板。

Orrery 执行：

  • Recruiting Agent 初筛候选人信息和岗位匹配点。
  • Scheduling Agent 协调面试时间。
  • Interview Ops Agent 收集面试反馈。
  • PM / HR Agent 汇总候选人状态。
  • QA Agent 检查是否缺少评价、审批或录用依据。

交付物：

  • 候选人推进看板。
  • 每位候选人的简历摘要和匹配理由。
  • 面试安排记录。
  • 面试反馈汇总。
  • 决策建议和风险提示。
  • Offer / 淘汰 / 待定清单。

客户购买理由：

很多中小企业招聘不是没有候选人，而是推进混乱、反馈丢失、业务方不回复。Orrery 卖的是“候选人推进到结果”。

14.4 运维场景一：账号开通与权限变更包

适用客户：使用多个 SaaS、内部系统、代码仓库、云服务和业务后台的团队。

客户输入：

  • 申请人。
  • 申请原因。
  • 目标系统。
  • 权限范围。
  • 有效期。
  • 审批人。

Orrery 执行：

  • IT Ops Agent 检查申请信息是否完整。
  • Policy Agent 判断是否需要主管、系统 owner 或安全负责人审批。
  • Approval Agent 推送审批请求并记录结果。
  • Tool Agent 生成账号开通或权限变更操作清单。
  • QA Agent 检查权限是否按范围、按期限完成。

交付物：

  • 权限申请记录。
  • 审批链路。
  • 执行记录。
  • 有效期和回收提醒。
  • 异常权限和风险提示。
  • 审计证据包。

客户购买理由：

账号权限是企业最常见、最琐碎也最容易出风险的运维任务。Orrery 先把流程跑顺，再逐步接入自动化和 MCP Gateway。

14.5 运维场景二：故障协同与复盘包

适用客户：有线上系统、内部工具、门店设备、客服系统或业务后台的团队。

客户输入：

  • 故障描述。
  • 发生时间。
  • 影响范围。
  • 相关系统。
  • 当前处理人。
  • 沟通群或工单链接。

Orrery 执行：

  • Incident Agent 建立故障 Mission。
  • Triage Agent 收集现象、影响范围、日志和截图。
  • Ops Agent 分配排查任务。
  • 通知 Agent 给业务方和负责人同步进展。
  • HIL 节点处理重启、回滚、权限提升等高风险动作。
  • Review Agent 汇总原因、处理过程和复盘建议。

交付物：

  • 故障时间线。
  • 影响范围说明。
  • 排查任务和责任人。
  • 关键证据。
  • 处理动作和审批记录。
  • 复盘报告。
  • 后续改进任务。

客户购买理由：

故障处理中最贵的不是修复动作，而是信息混乱、责任不清、复盘缺失。Orrery 把故障协同变成可交付过程。

14.6 运维场景三：资产盘点与异常追踪包

适用客户：有办公设备、门店设备、云资源、SaaS 账号、软件许可证的团队。

客户输入：

  • 资产台账。
  • 设备或账号清单。
  • 负责人名单。
  • 盘点周期。
  • 异常处理规则。

Orrery 执行：

  • Asset Agent 生成盘点任务。
  • 通知 Agent 向负责人收集确认。
  • Ops Agent 标记闲置、丢失、未归属、重复购买等异常。
  • Approval Agent 推动报废、回收、续费或停用审批。
  • QA Agent 检查盘点证据和异常闭环。

交付物：

  • 资产盘点报告。
  • 异常资产清单。
  • 负责人确认记录。
  • 回收、停用、续费或报废建议。
  • 审批和处理证据。
  • 下一轮跟踪任务。

客户购买理由：

资产盘点通常没人愿意做，也很难闭环。Orrery 可以把它包装成周期性项目交付。

14.7 可销售的首批任务包

第一阶段建议把产品包装为 3 个项目化任务包：

任务包面向客户典型周期交付结果
入转调离协同包HR / 行政 / IT1-4 周入职、转岗、离职任务闭环和证据包
账号权限治理包IT / 运维 / 安全1-4 周权限申请、审批、开通、回收和审计记录
工单与故障协同包IT / 运维 / 业务支持1-2 周工单推进、故障时间线、处理证据和复盘

这三个任务包共同特点是：高频、刚需、流程明确、结果可验收、容易项目化收费，也能逐步引出权限、HIL、工具网关和 Agent Directory。

14.8 示例销售话术

对 HR 负责人：

我们不是替换你的 HR 系统，而是帮你把入职、离职、转岗这类跨部门事务推进到底。
每个事项谁负责、做到哪一步、缺什么材料、哪些权限没关、哪些设备没回，都能形成可审计交付包。

对 IT / 运维负责人：

我们不是再做一个工单系统，而是帮你把账号权限、故障协同、资产盘点这类需要多人推进的任务变成可追踪、可审批、可复盘的交付流程。
后续如果要接入自动化脚本、内部工具或 MCP，也可以自然升级。

对老板或管理者：

很多内部事务不是没人做，而是没人跟到底、没人留证据、出了问题不知道卡在哪里。
Orrery 让真人和 Agent 一起把这些事务推进到可验收结果。

16. 商业模式

Orrery 早期应尽量项目化收费，不急于设计复杂标准定价。客户先为“某类人事/运维任务被稳定交付”付费，而不是为抽象平台功能付费。

收费方式阶段说明
项目化交付最早期围绕人事/运维任务包报价，例如入转调离、账号权限治理、工单协同等
按 Mission / 任务包收费早期每个可审计任务交付包一个价格
工作台订阅产品化后按团队席位、Agent 数量、Mission 数量收费
Agent / Tool 运行额度使用增长后按 Agent run、工具调用、证据存储、上下文处理收费
HIL / 审批中心高风险业务流程按审批席位、请求量、SLA、流程数量收费
MCP Gateway 治理企业接入后作为后续收费方向，按 MCP server、tool call、审计日志、凭证托管收费
企业私有化 / 混合部署中后期面向安全、合规、私有系统接入需求
行业模板包成熟后人事、运维、行政、财务、法务等任务模板

早期不建议把“Agent 市场”作为主要收入。市场是供给增长后的结果，不是第一天的商业核心。

17. Go-to-market 路径

阶段一：服务化验证

先用人工 + Agent 半自动方式交付真实的人事/运维任务，验证客户是否愿意为可信交付按项目付费。

重点不是自动化程度，而是交付包质量、证据完整度、责任清晰度和客户验收体验。

阶段二：产品化 Mission Control

把 Mission、Team、Task、Evidence、QA、Timeline 固化为工作台。

让客户能看到：

  • 谁在做。
  • 做到哪里。
  • 交付了什么。
  • 有什么证据。
  • 哪些任务失败或返工。
  • 最终是否可验收。

阶段三：组织化 Agent Directory

建立可调度的 Agent / RealHumanAgent 目录。

让系统能回答：

  • 这个任务需要哪些角色？
  • 哪些 Agent 适合？
  • 哪些真人需要参与？
  • 谁负责最终结果？

阶段四：权限、HIL 与工具网关

把高风险工具调用、审批、人类补充信息、权限拦截接入任务执行链路。MCP Gateway 在这一阶段作为能力演进，不作为第一阶段宣传入口。

这一步让 Orrery 从交付工作台升级为企业 Agent 控制面。

阶段五：评价与运营系统

沉淀人、Agent、Squad、工具、任务模板的表现数据，形成持续优化和组织运营能力。

18. 北极星指标

Orrery 的核心指标应该围绕“可信交付”和“组织控制”设计。

建议北极星指标：

可审计完成的 Mission 数量

配套指标：

  • Mission 验收通过率。
  • 单位 Mission 交付成本。
  • 平均返工次数。
  • Agent / 真人混编任务完成率。
  • 每个 Mission 的 evidence 完整度。
  • 高风险工具调用被正确审批或拦截次数。
  • HIL 平均响应时间。
  • 客户验收时间下降比例。
  • Agent 复用率。
  • 任务模板复用率。

19. 客户购买理由

客户愿意购买 Orrery，不是因为它“更 AI”，而是因为它降低了 AI 进入真实业务的管理成本和风险。

核心购买理由：

  • 降低多 Agent、多工具、多真人协作成本。
  • 让任务结果可验收，而不是只看 Agent 总结。
  • 降低权限、凭证、误调用和数据泄露风险。
  • 缩短客户验收时间。
  • 减少返工和沟通噪音。
  • 让管理者看到责任、证据和 ROI。
  • 让企业可以逐步扩大 Agent 使用范围。

20. 不做什么

Orrery 必须保持边界清晰。

我们不做：

  • 不做基础模型。
  • 不做通用聊天机器人。
  • 不做另一个软件开发 Agent。
  • 不使用“Agent 公司”作为对外主品牌词，避免被限制在概念化或单一形态里。
  • 不做重型 HRIS。
  • 不做薪资、考勤、社保。
  • 不做裸 workflow builder。
  • 不做无责任、无审计的全自动系统。
  • 不和 Codex、Claude Code、Cursor、Agentforce 正面比较单点执行能力。

我们的路线是接入它们、管理它们、约束它们、验收它们。

22. 已确认决策与待讨论问题

根据当前讨论，以下关键方向已经确认。

22.1 已确认：第一 wedge

第一阶段不直接切企业 AI CoE / MCP Gateway 治理，避免陷入无尽适配、集成、安全评审和平台化需求。

当前第一 wedge 是：

人事与运维场景的项目化、可审计任务交付。

22.2 已确认：对外品牌词

对外不使用“Agent 公司”作为主品牌词，避免把产品限制在单一概念里。正式对外更适合主打：

人机共生组织控制平台
AI Workforce Control Plane
Human-Agent Organization Control Plane

22.3 已确认：MCP Gateway 不是当前主打

MCP Gateway 是后续收费方向和企业版能力，不作为当前主打。当前主打是人事/运维任务的可信交付、责任划分、证据链和审批留痕。

22.4 已确认：主要场景

主要场景收窄到：

人事
运维

22.5 已确认：重点写竞争优势

企划书需要继续补强竞争优势，而不是把重心放在定价或成功案例上。

22.6 已确认：收费先项目化

当前不展开复杂定价，先按项目化交付理解。后续再根据人事/运维任务包沉淀标准化价格。

22.7 暂不展开：成功案例

成功案例暂不优先设计。等第一 wedge 和目标任务包更明确后再补。

22.8 已补充：人事/运维的首批任务包
