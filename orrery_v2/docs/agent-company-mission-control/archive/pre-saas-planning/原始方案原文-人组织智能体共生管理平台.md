# Orrery 人、组织、智能体共生管理平台总规划与竞品分析

日期：2026-05-29

## 1. 一句话定位

Orrery 不应该只做 Agent Mission Control，也不应该做成传统 HRIS。更有价值的方向是：

```text
人、组织、智能体共生的组织管理与执行控制平台
```

它的核心能力是把人、组织、Agent、Squad、任务、审批、权限、HIL、MCP 工具调用放进同一个管理基座里。

目标不是“给 Agent 多一个看板”，而是让企业能够回答这些问题：

- 谁是这个组织里的真实人员？
- 哪些 Agent 是组织成员？
- 人和 Agent 如何组成 Squad？
- 谁能把任务交给哪个 Agent？
- Agent 可以调用哪些 MCP 工具？
- 哪些动作需要人审批或 HIL？
- 谁授权了哪个 Agent 做了什么？
- 人和 Agent 的表现如何评估？
- 下游 MCP 生态如何安全、低成本、可审计地接入？

## 2. 当前 Orrery 基线

从代码看，Orrery 已经有一部分基础：

- 有 `workspace`、`member`、`agent`、`issue`、`agent_task_queue` 等核心表。
- 有 `squad`、`squad_member`，并且 squad 成员已经可以是 agent 或 member。
- 有 `agent.mcp_config`，说明 Agent 已经可以携带 MCP 配置。
- 有 QA contract / QA review，已经出现 Agent 任务质量评价雏形。
- 前端已有 `skills`、`squads`、`autopilot`、`workspace-admin` 等入口。
- 但 runtime 层存在自动放行权限请求的实现，例如 Claude 使用 `bypassPermissions`，Hermes 对 `session/request_permission` 自动 `approve_for_session`。

所以当前 Orrery 更像：

```text
Agent + Squad + Issue + Runtime 的任务执行平台
```

还缺少：

- 人员主数据。
- 组织树。
- 统一 Actor 模型。
- 组织权限。
- 审批流。
- HIL Inbox。
- MCP Gateway。
- 人和 Agent 的统一评价体系。
- 企业级审计和治理。

## 3. 总体产品结构

建议把系统分成七个一级模块：

```text
1. People Master Data
2. Organization Graph
3. Agent & Squad Management
4. Work / Mission Control
5. Permission & Policy Center
6. Approval / HIL Center
7. MCP Gateway & Audit Console
```

其中前四个解决“组织里有什么主体、怎么协作”，后三个解决“这些主体能不能安全地调用外部世界”。

## 4. 核心抽象：Actor

必须引入统一 Actor 概念，但第一阶段不建议推倒重建所有表。

建议保留现有：

- `user`
- `member`
- `agent`
- `squad`

新增统一引用模型：

```text
actor_type: person | agent | squad | org_role | workspace_member
actor_id: uuid
```

这个模型用于：

- 任务分配。
- 组织成员。
- 审批节点。
- HIL 处理人。
- 权限授予。
- MCP 调用主体。
- 评价对象。
- 审计主体。

不要把 Agent 假装成人，也不要把人和 Agent 混成一张实体表。正确做法是：实体分开，组织协作层统一引用。

## 5. 模块设计

### 5.1 人员主数据 People Master Data

目标：建立真实人员档案，但不做重型 HRIS。

核心能力：

- 人员基础信息：姓名、工号、邮箱、手机号、头像、状态。
- 雇佣信息：入职、离职、用工类型、岗位、职级。
- 组织归属：主组织、兼职组织、上级、汇报线。
- 人员数据子集：教育、履历、技能、证书、合同、外部账号。
- 人员状态：在职、离职、冻结、外包、访客。

建议数据表：

```text
person_profile
person_subset_schema
person_subset_record
person_external_identity
```

第一版不要做复杂 HR 流程，只做组织协作需要的人档案。

### 5.2 组织管理 Organization Graph

目标：让人和 Agent 都能成为组织成员。

核心能力：

- 新建组织。
- 组织树维护。
- 组织移动、排序、停用。
- 组织负责人可以是人，也可以是 Agent。
- 组织成员可以是 person、agent、squad。
- 支持主组织、兼职组织、虚拟组织、项目组织。

建议数据表：

```text
org_unit
org_membership
org_role
org_role_assignment
org_relation
```

关键点：

- 组织树不是展示组件，而是权限、审批、任务分配、评价的基础。
- 组织负责人、项目负责人、资源 owner 都应该进入权限判断。

### 5.3 Agent 与 Squad 管理

目标：从“Agent 列表”升级为“组织内智能体岗位体系”。

核心能力：

- Agent 档案：名称、角色、能力、所属组织、owner、状态。
- Agent 能力：技能、工具、MCP 权限、模型、运行时。
- Agent 岗位：PM Agent、Reviewer Agent、Research Agent、Ops Agent。
- Squad 混编：人 + Agent 组成小队。
- Squad leader 可以是人，也可以是 Agent。
- Agent 生命周期：创建、试运行、批准上岗、停用、归档。

建议新增：

```text
agent_profile_extension
agent_capability
agent_org_assignment
agent_lifecycle_event
squad_role_requirement
```

### 5.4 Work / Mission Control

目标：继续保留 Orrery 当前强项，把任务、issue、project、autopilot、squad 串起来。

核心能力：

- 任务可以分配给 person / agent / squad。
- 任务可以触发审批。
- 任务可以触发 MCP tool call。
- Squad leader 负责拆任务、分派、汇总。
- Autopilot 需要绑定权限和 HIL 策略。
- Mission 可以有目标、约束、预算、风险等级。

建议发展方向：

- 从 issue assignee 扩展到 actor assignee。
- 从 agent task queue 扩展到 human-agent work queue。
- 从 QA review 扩展到 evaluation evidence。

### 5.5 权限中心 Permission & Policy Center

目标：成为人和 Agent 的统一授权中心。

不要只做 RBAC。建议组合：

```text
RBAC: owner/admin/member/hr/finance/reviewer
ABAC: 部门、岗位、数据等级、风险等级、环境
ReBAC: 上级、组织负责人、项目owner、资源owner
Capability: github.read、github.write、slack.send、mcp.query
Scope: repo、目录、组织、项目、客户、系统
Context: 当前任务、审批单、会话、时间、预算
```

建议数据表：

```text
policy_rule
policy_binding
actor_capability
actor_capability_grant
resource_scope
policy_decision
```

最小决策结果：

```text
allow
deny
needs_hil
needs_approval
needs_input
needs_elevated_scope
```

关键原则：

- Agent 不能自己给自己授权。
- Prompt 不是安全边界。
- OAuth 只解决登录授权，不解决业务动作授权。
- 权限判断必须有可审计结果。

### 5.6 审批与 HIL Center

目标：让人类介入成为产品能力，而不是运行时临时弹窗。

HIL 类型：

```text
Tool Permission HIL
Business Approval HIL
Data Elicitation HIL
Risk Exception HIL
Delegation HIL
Review HIL
```

HIL 操作：

- 批准本次。
- 批准本会话。
- 拒绝。
- 要求修改。
- 补充信息。
- 转交。
- 升级为正式审批。

审批节点类型：

```text
person
agent
org_role
squad
system
external_approver
```

审批模式：

- 串行。
- 并行。
- 任一通过。
- 多数通过。
- 条件分支。
- 超时转交。

建议数据表：

```text
hil_request
hil_response
hil_assignment
approval_definition
approval_request
approval_node
approval_action
```

### 5.7 MCP Gateway & Audit Console

目标：让 Orrery 成为下游 MCP 生态的友好入口。

调用链：

```text
Agent Runtime
  -> Orrery MCP Gateway
  -> Policy Decision
  -> HIL / Approval if needed
  -> Downstream MCP Server
```

核心能力：

- MCP Server 注册。
- Tool 发现。
- Tool 风险标注。
- Tool schema 管理。
- OAuth / token / secret 托管。
- STDIO MCP wrapper。
- HTTP MCP reverse proxy。
- 每次 tool call 权限决策。
- 每次 tool call 审计。
- 参数摘要、结果摘要、耗时、成本、DLP 命中。

建议数据表：

```text
mcp_server
mcp_tool
mcp_resource
mcp_tool_risk_profile
mcp_session
mcp_call
credential_vault_ref
audit_event
```

## 6. 评价体系

人和 Agent 可以共用评价框架，但不能共用同一套指标。

### 6.1 人的评价

维度：

- 目标完成。
- 协作质量。
- 专业能力。
- 响应与可靠性。
- 管理/带教。
- 同事反馈。
- 自评与经理评价。

### 6.2 Agent 的评价

维度：

- 任务成功率。
- QA 分数。
- 返工次数。
- 人工接管率。
- HIL 触发率。
- 越权尝试率。
- 成本。
- 时延。
- 工具调用成功率。
- 用户满意度。

建议数据表：

```text
evaluation_template
evaluation_cycle
evaluation_record
evaluation_evidence
agent_metric_snapshot
person_review_snapshot
```

关键原则：

- 人的评价要有隐私边界。
- Agent 的评价要可量化。
- 不要把人和 Agent 放在一个粗暴排行榜里。
- 评价证据可以来自任务、审批、HIL、QA、MCP 调用日志。

## 7. 竞品调研总览

这一章不要按“谁和 Orrery 最像”来读。现在市场上还没有一个产品完整覆盖“人 + 组织 + Agent + HIL + MCP Gateway”。更合理的读法是把竞品拆成能力拼图：

```text
HR/HCM 给人和组织模型
工作管理平台给任务图和协作上下文
企业 Agent 平台给 AI 工作流和业务动作
MCP/HIL/权限产品给安全控制面
Mission Control 产品给多 Agent 执行体验
通用 AI 工作空间给最终产物体验
```

Orrery 的机会不是复制其中某一个，而是把这些能力组合成一个新类目。

### 7.0 先看结论

#### 7.0.1 竞品分层地图

| 层级 | 代表产品 | 它们真正解决的问题 | Orrery 应该吸收的能力 |
|---|---|---|---|
| 人和组织事实源 | Workday、Rippling、BambooHR、HiBob | 谁是员工、属于哪个组织、有什么岗位和权限基础 | 人员主数据、组织树、岗位/角色、组织变更触发权限变更 |
| 绩效和反馈 | Lattice、Culture Amp、15Five | 人的目标、反馈、绩效和成长 | 评价周期、评价模板、证据、反馈闭环 |
| 工作图和 AI Teammate | Asana、Rovo、Glean | AI 在真实任务、知识、项目里协作 | Work Graph、知识权限、任务上下文、AI teammate 体验 |
| 企业 Agent 平台 | Copilot Studio、Agentforce、ServiceNow、UiPath | AI 进入企业流程并产生动作 | Agent flow、AI approval、HIL、资产治理、流程恢复 |
| MCP/权限/HIL 基础设施 | Permit、Pomerium、Arcade、HumanLayer、OpenFGA | Agent 调用工具前的授权、凭证、审批和审计 | MCP Gateway、tool call 授权、HIL Inbox、ReBAC、审计 |
| Agent Mission Control | Factory、Cline、OctoAlly | 多 Agent 执行任务、会话、代码和结果交付 | Mission、调度、运行状态、验收、开发者体验 |
| 通用 AI 工作空间 | Genspark、Manus、Zapier Agents | 普通用户把任务交给 AI 得到产物 | 结果产物导向、模板化工作流、低门槛入口 |

#### 7.0.2 对 Orrery 最重要的五个判断

1. **Workday / Rippling 证明了“人和组织事实源”很重要**
   但 Orrery 不应该做薪资、假勤、复杂人事事务。Orrery 只需要做“协作和权限所需的人员主数据”。

2. **Asana / Rovo / Glean 证明了 Agent 必须进入真实工作图**
   Agent 不能只是聊天窗口。它要知道项目、任务、目标、组织、知识和权限。

3. **Permit / Pomerium / Arcade 证明 MCP 生态需要统一控制面**
   下游 MCP Server 不应该各自重复实现企业权限、凭证、审批和审计。Orrery 可以承担这一层。

4. **HumanLayer / UiPath / Copilot Studio 证明 HIL 要产品化**
   HIL 不是弹窗，而是一个有 SLA、有状态、有上下文、可恢复执行流的操作中心。

5. **Factory / Genspark 证明用户最终关心结果，不关心 Agent 日志**
   Orrery 需要保留 mission control，但最终要交付任务结果、报告、文件、审批结论和可追溯证据。

#### 7.0.3 最值得优先对标的产品

| 优先级 | 产品 | 原因 |
|---|---|---|
| P0 | Permit MCP Gateway | 最接近 Orrery 的 MCP 权限和审计控制面 |
| P0 | HumanLayer | 最直接的 HIL request / decision layer 参考 |
| P0 | Asana AI Teammates | 最适合参考“AI 在工作图里协作” |
| P0 | Workday / Rippling | 用来校准人和组织模型的严肃性 |
| P0 | ServiceNow AI Control Tower | 用来参考 AI/MCP 资产治理和审批 |
| P1 | Arcade | 用来参考 MCP runtime、OAuth、token、工具市场 |
| P1 | OpenFGA/Auth0 FGA | 用来参考 ReBAC 权限表达 |
| P1 | UiPath Action Center | 用来参考人工操作中心和流程恢复 |
| P1 | Factory | 用来参考 Mission / 多 Agent 执行体验 |
| P2 | Genspark / Manus / Zapier Agents | 用来参考低门槛 AI 工作空间和最终产物体验 |

#### 7.0.4 不建议照搬的方向

- 不要照搬 Workday：太重，容易偏成人事系统。
- 不要照搬 Asana：它的核心是项目管理，Orrery 的核心应是人机组织控制面。
- 不要照搬 ServiceNow：企业治理很强，但产品会变重。
- 不要照搬 Factory：开发场景强，但不覆盖通用组织管理。
- 不要只学 Permit：MCP 安全很强，但缺少人、组织、任务和评价。

### 7.1 HR/HCM 类

这一类竞品的价值不是 AI，而是“组织事实源”。Orrery 要从这里学习人员、组织、岗位、变更、评价的严肃性，但不要进入薪资、考勤、复杂人事流程。

#### Workday

一句话判断：Workday 是大型企业的人和组织事实源，不是 Agent 平台。

强项：

- HCM 主数据。
- 组织管理。
- 岗位、技能、绩效。
- 企业流程和审批。
- 大型企业治理。

对 Orrery 的启发：

- 人员和组织模型要严肃，不能只做通讯录。
- 组织、岗位、技能、绩效要能服务任务和权限。

不足：

- 不是 Agent 原生。
- 不管理 MCP 工具调用。
- 过重，不适合作为 Orrery 的产品形态。

#### Rippling

一句话判断：Rippling 的关键不是 HRIS 本身，而是“员工数据驱动 IT、应用、权限和流程自动化”。

强项：

- 员工主数据。
- 应用账号、设备、权限、流程自动化。
- 员工图谱连接 HR、IT、Finance。

对 Orrery 的启发：

- 人员变动应该联动权限。
- 入职、转岗、离职会影响 Agent/MCP 访问范围。

不足：

- 重点是人和企业 SaaS，不是 Agent/MCP。

#### BambooHR / HiBob

一句话判断：BambooHR / HiBob 更适合参考中小团队的人事体验和组织图，而不是复杂企业套件。

强项：

- 员工档案。
- 组织图。
- 审批。
- 绩效、反馈、假勤、People Analytics。

对 Orrery 的启发：

- 人员主数据和组织树要简单易用。
- 中小企业版本不要做得像 Workday 一样重。

不足：

- 没有智能体组织成员概念。

#### Lattice / Culture Amp / 15Five

一句话判断：这类产品解决“人怎么被评价和发展”，适合为 Orrery 的评价中心提供模板思路。

强项：

- 绩效评价。
- 目标。
- 反馈。
- 1:1。
- 组织健康度。

对 Orrery 的启发：

- 评价体系不能只有任务完成率。
- 人的评价需要周期、维度、证据和反馈。

不足：

- 不管理组织权限和 Agent 执行。

### 7.2 工作管理 + AI Teammate 类

这一类最值得学的是“AI 要嵌入工作图”。它们不把 Agent 当孤立机器人，而是让 AI 理解任务、项目、目标、知识和协作关系。

#### Asana AI Teammates

一句话判断：Asana 最值得借鉴的是 Work Graph，不是看板 UI。

强项：

- AI teammate 嵌入 work graph。
- 任务、项目、上下文和协作关系清晰。

对 Orrery 的启发：

- Agent 应该在真实任务图里工作，不应该孤立聊天。
- Work graph 是 Agent 协作的底座。

不足：

- 人员主数据和 MCP 权限不是核心。

#### Atlassian Rovo

一句话判断：Rovo 的价值在于把 Agent 放进 Jira / Confluence 的知识和工作流里。

强项：

- Jira / Confluence 知识图谱。
- Rovo Agents。
- 工作上下文和企业搜索。

对 Orrery 的启发：

- Agent 需要组织知识和任务上下文。
- 企业搜索、知识权限和 Agent 行动应该结合。

不足：

- 重 Atlassian 生态，不是通用 MCP Gateway。

#### Glean Agents

一句话判断：Glean 的核心启发是“Agent 行动必须继承企业数据源权限”。

强项：

- 企业搜索。
- 连接器。
- 知识权限。
- Agents 和 actions。

对 Orrery 的启发：

- 权限继承和数据源权限非常重要。
- Agent 调用工具时要尊重原系统权限。

不足：

- 更偏知识和搜索，不是组织管理平台。

### 7.3 企业 Agent 平台类

这一类说明大厂正在把 Agent 放进业务系统，但它们通常被各自生态绑定。Orrery 应该学它们的流程、审批、guardrails 和资产治理，不要学它们的封闭生态。

#### Microsoft Copilot Studio

一句话判断：Copilot Studio 最适合参考“人和 AI 混合审批流”。

强项：

- Agent flows。
- 用户认证。
- AI approvals。
- 人工信息请求。
- Power Platform 生态。

对 Orrery 的启发：

- 审批节点可以是人，也可以是 AI。
- Agent 可以处理 routine approval，人处理 exception approval。

不足：

- 生态绑定重。
- 不以 MCP 开放生态为核心。

#### Salesforce Agentforce

一句话判断：Agentforce 证明 Agent 必须围绕业务对象行动，而不是只围绕聊天上下文行动。

强项：

- CRM 数据和 workflow。
- Agent action。
- Guardrails。
- 企业业务场景落地。

对 Orrery 的启发：

- Agent 要进入业务对象和流程，而不是停留在对话。
- 权限、数据、操作都要围绕业务对象建模。

不足：

- 强依赖 Salesforce 数据和流程。

#### ServiceNow AI Control Tower / Agent Studio

一句话判断：ServiceNow 最适合参考 AI/MCP 资产治理和上架审批。

强项：

- AI asset 治理。
- Agent、model、workflow、MCP server 审批。
- 企业级生命周期和合规。

对 Orrery 的启发：

- MCP Server 上架本身也要审批。
- Agent 和 MCP 都应该进入资产目录。

不足：

- 太重，开发者和中小团队体验不轻。

#### UiPath

一句话判断：UiPath Action Center 是 HIL 操作台的成熟参照。

强项：

- RPA 自动化。
- Action Center。
- 人工动作中心。
- workflow suspend/resume。

对 Orrery 的启发：

- HIL 应该是操作台，不是临时提示。
- 人处理后流程要恢复原上下文。

不足：

- 偏 RPA，不是 Agent/MCP 原生。

### 7.4 MCP / HIL / 权限网关类

这一类是 Orrery 最需要重点研究的方向。原因是：只要 Agent 能调用 MCP 工具，就必须解决“谁授权、能做什么、什么时候要人介入、怎么审计”。

#### Permit MCP Gateway

一句话判断：Permit 是 Orrery 在 MCP 权限控制面上的最直接对标。

强项：

- MCP 前置授权。
- 每次 tool call 权限判断。
- RBAC、ABAC、ReBAC。
- agent-human-server-tool 审计链。

对 Orrery 的启发：

- MCP tool call 是权限决策点。
- human -> agent -> tool 的授权链必须可追溯。

不足：

- 不做人和组织管理。

#### Pomerium MCP

一句话判断：Pomerium 适合参考零信任代理和内部 MCP 安全暴露。

强项：

- 零信任 MCP 代理。
- OAuth bridge。
- 内部 MCP 安全暴露。
- 工具调用日志。

对 Orrery 的启发：

- Orrery Gateway 要保护下游 MCP，而不是要求 MCP 自己实现企业安全。

不足：

- 偏网络访问代理，不是组织协作系统。

#### Arcade.dev

一句话判断：Arcade 适合参考 MCP runtime、OAuth 和工具接入体验。

强项：

- MCP runtime。
- OAuth、token、secret 管理。
- 工具市场。
- agent 代表用户调用工具。

对 Orrery 的启发：

- 工具认证和工具授权要分开。
- Gateway 托管凭证，Agent 不接触真实 token。

不足：

- 不负责组织树和业务审批。

#### HumanLayer

一句话判断：HumanLayer 适合参考 HIL request 的对象模型。

强项：

- Agent HIL。
- 决策请求。
- 审批、拒绝、恢复流程。

对 Orrery 的启发：

- HIL request 是独立对象，需要状态、SLA、上下文和处理结果。

不足：

- 不是 MCP 权限网关。

#### OpenFGA / Auth0 FGA

一句话判断：OpenFGA 适合参考复杂组织关系下的权限表达方式。

强项：

- ReBAC。
- 关系元组。
- 细粒度权限。

对 Orrery 的启发：

- 组织负责人、项目 owner、资源 owner 这类关系权限要可表达。

不足：

- 只做权限决策，不做产品体验和 HIL。

### 7.5 AI Coding Mission Control 类

这一类和 Orrery 当前气质接近，但它们通常偏代码开发。Orrery 应该吸收 mission、dispatch、session、review、diff、验收等体验，同时把范围扩展到通用组织协作。

#### Factory AI

一句话判断：Factory 是多 Agent 软件工程任务编排的强参照。

强项：

- Droids。
- Missions。
- Dispatch。
- Fusion。
- Superset。
- AI 软件工程任务编排。

对 Orrery 的启发：

- Mission 是比 issue 更高层的执行单位。
- 多 Agent 协作需要上下文、调度、代码理解和结果验收。

不足：

- 更偏开发场景，不解决通用组织管理。

#### Cline Kanban

一句话判断：Cline Kanban 适合参考轻量任务板和开发者可控感。

强项：

- IDE 内任务板。
- AI coding agent 执行任务。
- 开发者工作流轻量。

对 Orrery 的启发：

- 人机协作的操作面要简单，不要全是后台配置。

不足：

- 不是企业权限和组织平台。

#### OctoAlly

一句话判断：OctoAlly 适合参考本地多 agent session 管理。

强项：

- 本地 AI coding session 管理。
- 多项目、多 agent、Git 操作、会话输出。

对 Orrery 的启发：

- 本地 agent session 的可视化和持久化很重要。

不足：

- 不处理组织、审批、MCP Gateway。

### 7.6 通用 Agent 工作空间类

这一类提醒 Orrery：用户不是为了看 Agent 运行过程而来，而是为了得到结果。长期看，Orrery 需要能把任务结果沉淀成文档、报告、表格、审批结论、代码变更或业务动作。

#### Genspark

一句话判断：Genspark 更像“AI 产物工作空间”，不是组织权限基座。

强项：

- Super Agent。
- 多步骤任务执行。
- AI Slides / Sheets / Docs 等工作产物。
- 面向普通用户的一站式 AI 工作空间。

对 Orrery 的启发：

- 用户最终要的是结果产物，不是只看 Agent 日志。
- 需要把任务执行、资料、文件、表格、报告产物串起来。

不足：

- 更偏个人/团队生产力，不是企业组织权限基座。
- 不以人和 Agent 共生组织管理为核心。

#### Manus / Zapier Agents

一句话判断：这类产品说明自动化动作和外部应用连接很重要，但组织责任和权限边界通常不够深。

强项：

- 自主任务执行。
- 连接外部应用。
- 自动化动作。

对 Orrery 的启发：

- Agent 调用外部系统要有清晰授权和审计。

不足：

- 组织主数据、组织树、评价体系不是核心。

## 8.1 从竞品到 Orrery 模块的翻译

竞品分析最终要落到产品模块，而不是停留在“谁强谁弱”。下面是建议的翻译关系。

### 8.1.1 People Directory

参考对象：

- Workday
- Rippling
- BambooHR
- HiBob

Orrery 要做：

- 做轻量人员主数据。
- 支持基础档案、组织归属、岗位、状态、外部身份。
- 支持人员数据子集，例如技能、证书、履历、合同、账号。

Orrery 不做：

- 薪资。
- 复杂考勤。
- 社保薪酬。
- 全量 HR 流程。

产品判断：

```text
People Directory 是权限、审批、组织协作的事实基础，不是 HR 套件。
```

### 8.1.2 Organization Graph

参考对象：

- Workday
- Rippling
- ServiceNow
- OpenFGA

Orrery 要做：

- 组织树。
- 组织角色。
- 汇报关系。
- 项目组织。
- 虚拟组织。
- 人和 Agent 都能加入组织。
- 组织关系进入权限和审批判断。

Orrery 不做：

- 只展示组织图。
- 把组织树做成静态通讯录。

产品判断：

```text
组织图不是页面，它是权限、审批、分派和评价的底层图谱。
```

### 8.1.3 Agent Directory

参考对象：

- Copilot Studio
- Agentforce
- ServiceNow Agent Studio
- Factory

Orrery 要做：

- Agent 档案。
- Agent 所属组织。
- Agent owner。
- Agent capability。
- Agent runtime。
- Agent 生命周期。
- Agent 可调用 MCP 工具范围。

Orrery 不做：

- 只展示 Agent 名称和模型。
- 让 Agent 无限继承创建者权限。

产品判断：

```text
Agent 应该像组织成员一样被管理，但责任边界必须和人分开。
```

### 8.1.4 Mixed Squad

参考对象：

- Asana AI Teammates
- Factory Missions
- 当前 Orrery Squad

Orrery 要做：

- 人和 Agent 混编。
- Squad leader 可以是人或 Agent。
- Squad 成员有角色和职责。
- Squad 可以被分配任务。
- Squad 可以触发审批和 HIL。

Orrery 不做：

- 只有 Agent 小队。
- 只有聊天群式协作。

产品判断：

```text
Mixed Squad 是人机共生组织的最小运行单元。
```

### 8.1.5 Work / Mission Control

参考对象：

- Asana
- Factory
- Cline Kanban
- OctoAlly
- Genspark

Orrery 要做：

- 任务。
- Mission。
- 子任务。
- 进度。
- Agent 执行状态。
- 人工接管。
- 结果产物。
- 验收和复盘。

Orrery 不做：

- 只看 agent logs。
- 只做开发场景。

产品判断：

```text
用户最终要的是可交付结果，不是 Agent 运行过程。
```

### 8.1.6 Permission Center

参考对象：

- Permit
- OpenFGA
- Rippling
- Glean
- Pomerium

Orrery 要做：

- RBAC。
- ABAC。
- ReBAC。
- Capability grant。
- Resource scope。
- Session grant。
- Policy decision。

Orrery 不做：

- 只有 workspace role。
- 只靠 prompt 约束 Agent。
- 让 MCP Server 各自实现权限。

产品判断：

```text
权限中心要回答的不是“用户能不能登录”，而是“这个 Agent 此刻能不能代表这个人调用这个工具处理这个资源”。
```

### 8.1.7 HIL / Approval Center

参考对象：

- HumanLayer
- UiPath Action Center
- Copilot Studio
- ServiceNow
- OpenAI Agents SDK

Orrery 要做：

- HIL Inbox。
- 审批请求。
- approve once。
- approve session。
- reject。
- request input。
- transfer。
- workflow resume。
- 审批节点支持人和 Agent。

Orrery 不做：

- 只有弹窗。
- 只有“同意/拒绝”。
- 没有上下文的审批。

产品判断：

```text
HIL 是 Agent 执行系统的一部分，不是 UI 附件。
```

### 8.1.8 MCP Gateway

参考对象：

- Permit MCP Gateway
- Pomerium MCP
- Arcade
- Portkey
- Cloudflare AI Gateway

Orrery 要做：

- MCP Registry。
- Tool discovery。
- Tool risk profile。
- Credential vault。
- HTTP MCP proxy。
- STDIO MCP wrapper。
- Tool call authorization。
- Tool call audit。
- DLP / cost / latency / error monitoring。

Orrery 不做：

- 让 Agent 直接持有长期 token。
- 把 MCP config 当成普通文本字段结束。
- 只记录成功调用，不记录被拒绝调用。

产品判断：

```text
MCP Gateway 是 Orrery 面向下游 MCP 生态的安全入口和开发者入口。
```

### 8.1.9 Evaluation Center

参考对象：

- Lattice
- Culture Amp
- Workday Performance
- 当前 Orrery QA Review
- ServiceNow AI governance

Orrery 要做：

- 人的评价模板。
- Agent 的评价模板。
- Squad 的评价模板。
- 任务证据。
- HIL 证据。
- MCP 调用证据。
- QA 证据。

Orrery 不做：

- 把人和 Agent 放进同一张排行榜。
- 用监控数据粗暴评价人。

产品判断：

```text
人和 Agent 可以共享评价框架，但不能共享同一套评价指标。
```

## 8.2 阅读者应该带走的产品判断

如果只保留五句话，应该是：

1. Orrery 的核心不是 HR，也不是 Agent IDE，而是人机共生组织控制面。
2. 人员主数据和组织树是权限、审批、评价的基础，不是附属页面。
3. Agent 必须被当作组织成员管理，但不能拥有和人一样的责任边界。
4. MCP Gateway + HIL 是 Orrery 最可能形成壁垒的地方。
5. MVP 应该优先跑通“人/组织/Agent -> 任务 -> MCP 调用 -> HIL -> 审计”的闭环。

## 9. Orrery 的差异化定位

Orrery 的机会不在单点功能领先，而在组合：

```text
HRIS 的人和组织
+ Agent Mission Control 的执行能力
+ MCP Gateway 的工具生态入口
+ HIL/审批的安全控制
+ Evaluation 的人机表现反馈
```

这类产品可以定义为：

```text
Human-Agent Organization Operating System
```

中文定位：

```text
人机共生组织操作系统
```

差异化点：

- 不是只管人，也管 Agent。
- 不是只管 Agent，也管组织责任。
- 不是只管任务，也管授权、审批、审计。
- 不是只管 MCP 工具，也管谁代表谁调用工具。
- 不是只看执行结果，也评价人和 Agent 的协作质量。

## 10. 建设路线

### P0：现状收敛与基础抽象

目标：不推倒现有系统，先形成统一语言。

要做：

- 定义 `actor_type + actor_id`。
- 梳理现有 member / agent / squad / issue assignee 的兼容方式。
- 把自动 approve 的 runtime 行为列为安全债务。
- MCP/HIL 先做审计，不立刻阻断所有调用。

交付：

- Actor 引用规范。
- 现有表和新模型映射表。
- 安全债务清单。

### P1：人员主数据与组织树

目标：建立人和组织的基础。

要做：

- `person_profile`。
- `person_subset_schema` / `person_subset_record`。
- `org_unit`。
- `org_membership`。
- 人和 Agent 都可加入组织。
- 组织树 UI。

交付：

- People Directory。
- Organization Tree。
- 组织成员管理。

### P2：Agent 组织化与混编 Squad

目标：把 Agent 从工具升级为组织成员。

要做：

- Agent 所属组织。
- Agent owner。
- Agent capability。
- Squad leader 支持人或 Agent。
- Squad 成员角色要求。

交付：

- Agent Directory。
- Squad Roster。
- 混编团队视图。

### P3：权限中心

目标：让所有主体的能力边界可配置。

要做：

- actor capability。
- resource scope。
- policy rule。
- policy decision。
- RBAC + ABAC + ReBAC 的简版组合。

交付：

- Permission Center。
- Policy Decision API。
- 权限审计记录。

### P4：HIL Inbox 与审批流

目标：把人工介入产品化。

要做：

- HIL request。
- HIL Inbox。
- approve once / approve session / deny / input / transfer。
- approval definition。
- approval request。
- 审批节点支持人和 Agent。

交付：

- HIL Inbox。
- Approval Center。
- Agent 执行暂停和恢复。

### P5：MCP Gateway

目标：对下游 MCP 生态友好。

要做：

- MCP Registry。
- Tool discovery。
- Tool risk profile。
- HTTP MCP proxy。
- STDIO MCP wrapper。
- credential vault。
- tool call policy enforcement。

交付：

- MCP Control Center。
- MCP tool call 审计。
- 下游 MCP 安全接入规范。

### P6：评价中心

目标：形成闭环。

要做：

- evaluation template。
- evaluation record。
- evaluation evidence。
- 人的周期评价。
- Agent 的任务评价。
- Squad 的协作评价。

交付：

- Evaluation Center。
- Agent performance dashboard。
- Human-Agent collaboration report。

## 11. 最小可行版本 MVP

建议 MVP 聚焦一个闭环，不要一次做完整平台。

MVP 范围：

```text
People Directory
Organization Tree
Agent Directory
Mixed Squad
Permission Decision
HIL Inbox
MCP Tool Audit
```

最小用户故事：

1. 管理员创建人员和组织。
2. 管理员把 Agent 加入组织。
3. 管理员创建人 + Agent 混编 Squad。
4. 用户把任务分配给 Squad。
5. Agent 执行任务时请求调用 MCP tool。
6. Gateway 判断需要 HIL。
7. 人在 HIL Inbox 批准本次调用。
8. Agent 继续执行。
9. Audit Console 记录完整链路。

这个闭环能证明平台价值。

## 12. 关键风险

### 12.1 做成重型 HRIS

风险：产品陷入员工档案、假勤、薪资、合同等传统 HR 需求。

控制：只做组织协作所需的人员主数据，不做薪资和复杂人事事务。

### 12.2 做成普通 Agent 看板

风险：只管理任务和日志，缺少组织和权限壁垒。

控制：把组织、权限、HIL、MCP Gateway 放在核心路径。

### 12.3 权限模型过早复杂化

风险：一开始做 DSL / OpenFGA / 全量策略语言，开发成本过高。

控制：先做结构化规则表，再逐步演进。

### 12.4 HIL 变成橡皮图章

风险：人只看到“是否批准”，看不到风险和上下文。

控制：HIL 必须展示调用者、目标、参数摘要、风险、预览、历史、理由。

### 12.5 Agent 获得过大权限

风险：Agent 继承人权限后越权行动。

控制：human consent、agent capability、resource scope、session grant 必须分开。

## 13. 推荐下一步

第一步不要写代码，先把产品拆成三份更细的实施文档：

1. `人员与组织模型实施方案`
2. `权限审批HIL与MCP网关实施方案`
3. `人机评价体系实施方案`

然后按 MVP 顺序进入开发：

```text
Actor规范
-> People / Org
-> Agent org assignment
-> Permission Decision
-> HIL Inbox
-> MCP Gateway audit
```
