# 自动维修的授权与审批边界

实现基点：`d76d0e5f6f7f153f35f32c3a3644aede2edb4242`。本次增量对应
ORR-AUTH-01/02、ORR-TOOLS-01、ORR-ACTION-01、ORR-REPAIR-01。
设计基线解释原有合同；最新用户要求和原业务委托优先。

## 决策顺序

真实入口身份 → 租户与组织归属 → 执行信封及工具/工作区授权 →
具体动作的业务审批 → 实际执行回执 → 原业务验收。

基础权限、业务审批、运行预算是三个独立条件。审批不能授予一个未绑定的工具、
扩大工作区、切换用户/租户或延长超时。任务长、步骤多、被称为维修、工具可见，
均不构成需要审批或已经授权的证据。

| 动作 | 所需条件 | 审批处理 |
|---|---|---|
| 只读诊断、检索设计和证据 | 当前真实主体具备对应数据及工具权限 | 不因耗时另申请继续执行审批 |
| 定向、可回滚的代码或配置维护 | 原维修委托明确授权，目标和工作区在现有边界内 | 不重复提交笼统维修审批；保留原合同特定门禁 |
| 不产生业务副作用的测试和验证 | 已授权工具、环境及资源预算 | 不另申请长任务审批 |
| 发布内容、外发消息、付费、凭据或权限变更 | 基础权限、具体业务授权及该动作要求的审批 | 维修委托不能替代业务合同、QA 或审批 |
| 审批他人的请求、修改审批策略、绕过 QA | 不属于普通维修授权 | 不因维修自动开放 |
| 超时、取消、预算耗尽 | 按运行状态和恢复策略处理 | 业务审批不能解除运行限制 |

## 已有服务端边界与本次调整

自动维修入口复用 `isAutomaticRepairRequest`：校验可信内部服务标记、system
主体、dispatcher ID、会话所有者和作者、租户、指定维修 Agent 及托管工作区。
普通聊天或模型提交的相同名字不能取得维修运行时。工具绑定、执行信封、数据 ACL、
工作区约束和原审批策略继续执行。本次不增加权限 scope，也不产生自动批准回执。

维修指派原本已声明普通维护不重复审批，但 `request_business_approval` 的旧说明
仍要求所有长任务先审批。本次统一工具说明、托管运行提示和原生 CLI bootstrap，
让 Agent 依据具体动作及原委托判断是否申请额外业务审批。提示用于解释规则，
并不替代服务端鉴权，也不能保证模型永远不会误申请。

## 审批责任人的租户归属

`productionHILAssigneeResolver` 对 Agent/真人申请先校验档案存在、ID 一致且启用。
普通租户请求要求申请人属于该租户；随后负责人、明确人选、
资源所有者、推荐人选和组织角色查询都限定在同一组织。

`system` 是内置共享流程模板和部分历史审批的存储命名空间，不是全组织管理员。
历史 `system` 审批以已验证申请人的组织约束全部人选，审批记录及回执仍留在原命名空间。
无组织的历史档案只属于旧 `system` 命名空间，不能匹配任意组织。
不依据标题、资源种类、模型声明或 `H000001` 的名称授予跨组织权限。

服务身份不冒充人员档案：普通服务请求使用已绑定的真实决策租户，并严格限制人选归属。
历史 `system` 公众号服务保留既有固定负责人合同；仅 `marketing` 服务身份、公众号草稿
审批动作、已解析的内置公众号模板、生成产物资源和原固定负责人同时匹配时才适用。
动作和模板由 workflow 服务传递，不从 Agent 工具参数读取。该明确业务合同不适用于
普通 Agent、维修、其他服务或 `global` 请求；其他共享命名空间服务缺少组织绑定时
返回 `approval_service_tenant_unbound`，不会自动开放全组织审批人。

严格组织约束只用于创建新流程时解析人选。已持久化的 `system` 审批通知、代理审批
及私助归属查询继续复用既有任务受让人/主人校验和原存储命名空间，不重新分配审批人，
以免旧合法审批的送达被误挡。通知可送达不代表创建新审批或扩大维修权限。

因此 `global` 维修请求不能自动交给 `minvia` 的 H000001；换用 `system`
也不能绕过。若确有跨组织的受保护业务动作，需要正式建立对应责任归属或独立的
显式委托合同。本次不会自动修改人员组织、指定默认审批人或给维修 Agent 扩权。

缺失或停用的申请人返回 `approval_requester_unavailable`；申请人跨租户返回
`approval_requester_tenant_mismatch`；缺失负责人返回 `approval_manager_missing`；
停用或错误档案返回 `approval_assignee_unavailable`；审批人跨组织返回
`approval_assignee_tenant_mismatch`。失败不生成授权回执、不向其他租户回退。

## 恢复与验收

同一受保护动作复用待审批记录与原幂等键。路由失败后保留具体原因和未完成状态，
不切换主体、不重复申请相同审批。可以独立完成的已授权诊断和验证继续执行。
原维修 worker 的 attention hold、上下文回执和独立业务验收保持不变。
不重放用户排除的历史任务或重写已有审批、运行、incident 和渠道消息。

分别记录技术恢复、原业务完成、Agent 公开正文、渠道送达，不能相互代替。
本次回归覆盖保存的提示升级与幂等、managed/Codex/Claude/Pi 提示构造、
组织内负责人和角色路由、跨租户及停用/缺失申请人的拒绝，以及原高风险两级审批。
生产上线证据在部署产物中独立记录；没有真实业务回执时不声称该业务已完成。
